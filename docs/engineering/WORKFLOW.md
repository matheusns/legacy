LEGACY-WORK-001/002 own baseline and architecture approval; LEGACY-WORK-013 gates product execution. Clone `legacy`, `legacy_mockups`, `legacy_app`, `legacy_verification_tooling`, and `legavia_sdlc_gui` into one parent directory. MCP tools are disabled in these registered role commands. Additional allocated writable repositories use `--add-dir`. The runner retains frozen repository policies, change/history/path audits, registered checks and operator-owned acceptance. Permission denials and structured provider errors block the run, even if earlier assistant text claimed completion. These tool/permission settings and audits are not a per-file OS sandbox; do not interpret provider prose as acceptance evidence. The model picker supports Default, Sonnet, Opus and Haiku; every Claude role permits the same explicit aliases. For each slice: approve controlled requirements and screen/state references; plan explicit repository access; prepare and inspect the frozen prompt; execute the allocated Development/UX/Verification role; inspect actual registered check results; start the application preview; capture desktop and phone views; run a separate read-only UX review; route findings into corrective work; establish regression baselines only after a human fidelity review; then perform the current-candidate acceptance gate. Agents do not commit, push or merge. Explicit WP acceptance authorizes the deterministic workbench to commit that WP’s fingerprinted implementation files and approval records, then push to origin/main. Other automatic control Git sync remains disabled.

The UX implementer owns fidelity within assigned presentation files. UX reviewers inspect the same pinned reference and candidate independently. A contract-changing UX finding creates a control-only SE predecessor before technical correction. Provider sandbox configuration restricts repository write roots; post-execution audits detect protected repository/history/path changes and preserve the working tree for inspection. This is not an OS-level per-file permission mechanism.

Screens and routes in the initial manifest are candidates derived from the reference shell. No screenshot asset is marked approved. Relevant source, suite, target-profile, fixture or approved-reference changes invalidate affected evidence. Device kind `emulated_browser` describes automated desktop/phone browser evidence; installed-PWA and actual/native-device observations need their own registered adapters.

Run the independent harness self-tests and GUI checks before changing command/report contracts. Update the source contract in this repository before changing acceptance semantics. The baseline reference files remain historical and are never overwritten for implementation convenience.

## Staged agent execution

New prepared Development runs use Analysis & Plan → Implementation → Verification → Independent Review → Handoff. The read-only `analysis` agent produces a bounded plan or an actionable blocker. The assigned write role implements it; the runner executes registered checks. Separate reviewers inspect the resulting candidate: `architecture_review` for SE, `code_style` and `design` for application development, `code_style` and `ux_review` for UI work, and `verification_review` for the independent harness. Design Review covers domain/API/integration boundaries, while Architecture Review owns controlled architecture and SE meaning. The new verification reviewer checks harness/report integrity without editing verifier code.

All roles emit concise public progress summaries and a final structured advisory. The workbench streams activity and persists real phase evidence; a runner heartbeat is distinct from an agent update. Planning/review commands and contract hashes are frozen with preparation. Read-only mutations, provider errors, failed registered checks and blocking review findings prevent a completed handoff. Reviews cannot grant acceptance; missing UX captures or actual-device observations remain explicit. Existing operator approval, repository access, branch/history/path audits remain in force; explicit acceptance now authorizes scoped runner-owned publication. Newly registered stage policies apply only after a fresh prompt is prepared.


## Publication after acceptance

`work_package_publication` enables commit/push after explicit WP acceptance, targeting `origin/main`. New preparations use the current branch, which must be main in all affected checkouts. The runner records per-file fingerprints; the reviewer acknowledges that exact scope before approval. Implementation files and generated control acceptance records are committed separately in their owning repositories. SE definition files changed by the run are included. Unrelated local drafts are excluded; unrelated staged changes, shared-manifest edits, stale candidates, ambiguous multi-WP runs and diverged history block publication rather than broadening its scope.

A publication failure does not undo an approval or discard a local commit. The review dialog records per-repository outcomes and offers Retry publication for the recorded candidate. Normal hooks run; commit scope/content is checked before push. No force-push, automatic rebase/reset, or credential mutation is permitted. Local CLI authentication and Git identity are prerequisites. GitHub publication across repositories is not atomic, so partial success must remain visible and retries must not create duplicate commits. Approval remains operator-owned and agents still have no authority to publish independently.
