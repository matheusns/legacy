# Website and phone development workflow

This manifest is the canonical engineering configuration for the five sibling GitHub checkouts. Candidate requirements retain their issued IDs and are not automatically approved. The existing 129 requirements, 15 capabilities, 35 use cases, 24 planned FVTs, and 13 work packages are preserved. LEGACY-WORK-001/002 own baseline and architecture approval; LEGACY-WORK-013 gates product execution. LEGACY-WORK-004 is assigned to the UX role and LEGACY-WORK-009 to the independent verification implementer. No status is promoted by this configuration migration.

Clone `legacy`, `legacy_mockups`, `legacy_app`, `legacy_verification_tooling`, and `legavia_sdlc_gui` into one parent directory. In verification tooling, run `npm ci` and `npx playwright install chromium`. In the GUI checkout, run `python -m pip install -e .`, then `sdlc-gui --manifest ../legacy/traceability/manifest.json`. Use `--validate-only` to inspect the definition without starting the server.

The GUI is a local engineering tool. The product preview is unconfigured until the application foundation exists and its real command is registered. The `tooling-fixture` suite exercises the verification harness only; it establishes no product compliance. Agent roles require an installed/authenticated Codex CLI on the GUI host. GitHub reviews require the host's `gh auth login`; the ChatGPT connector session is separate.

For each slice: approve controlled requirements and screen/state references; plan explicit repository access; prepare and inspect the frozen prompt; execute the allocated Development/UX/Verification role; inspect actual registered check results; start the application preview; capture desktop and phone views; run a separate read-only UX review; route findings into corrective work; establish regression baselines only after a human fidelity review; then perform the current-candidate acceptance gate. Commit/push/merge remain human-controlled. Automatic control Git sync is disabled.

The UX implementer owns fidelity within assigned presentation files. UX reviewers inspect the same pinned reference and candidate independently. A contract-changing UX finding creates a control-only SE predecessor before technical correction. Provider sandbox configuration restricts repository write roots; post-execution audits detect protected repository/history/path changes and preserve the working tree for inspection. This is not an OS-level per-file permission mechanism.

Screens and routes in the initial manifest are candidates derived from the reference shell. No screenshot asset is marked approved. Pin an approved PNG with `repository_id` (the canonical reference repository is `ux`), immutable full Git `revision`, `path`, and `status: approved` in `ux.screens[].references.<profile_id>` (`mobile-browser` or `desktop-browser`) after the reference review. Do not approve exploratory mockups by inference.

Product build/test/setup/cleanup commands and metric budgets are controlled in `verification_execution.suites`. A suite must emit a schema_version 1 report from real checks; missing/empty/invalid reports cannot pass. Relevant source, suite, target-profile, fixture or approved-reference changes invalidate affected evidence. Device kind `emulated_browser` describes automated desktop/phone browser evidence; installed-PWA and actual/native-device observations need their own registered adapters.

Run the independent harness self-tests and GUI checks before changing command/report contracts. Update the source contract in this repository before changing acceptance semantics. The baseline reference files remain historical and are never overwritten for implementation convenience.
